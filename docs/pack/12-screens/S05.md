# S05. Doc mode

> The same file, projected onto a page. A person who knows Google Docs can work here without
> learning markdown, and the bytes on disk stay markdown the whole time.

> **Ids invented here.** `14-COMPONENT-INVENTORY.md`, `16-COPY-DECK.md`,
> `17-ERROR-AND-REFUSAL-CATALOGUE.md`, `19-ACCEPTANCE-CRITERIA.md`,
> `55-MEASUREMENT-AND-EVENTS.md` and `56-OPEN-DECISIONS.md` are being written in parallel and did
> not exist when this file was written. Ids follow `65-CONVENTIONS.md` section 3 on a stated
> scheme derived from the screen number: components `C050` to `C059`, errors `E050` to `E059`, acceptance `A050` to `A059`. A component owned by another screen
> is cited by that screen's id. Copy ids are namespaced `K.s05.*`, so they cannot collide.

> **Error ids are provisional, and they clash.** `17-ERROR-AND-REFUSAL-CATALOGUE.md` now exists and
> is the home for every error id. It allocates by **category**, not by screen: engine `E001` to
> `E025`, validation `E030` to `E041`, permission `E050` to `E060`, quota `E070` to `E079`, model
> `E080` to `E087`, provider `E090` to `E097`, network `E100` to `E104`, conflict `E110` to `E117`.
> The `E` ids below were allocated from this screen's own block before that register existed, so
> many of them name a different error there. **Read them as descriptions, not as keys**, and
> reconcile each one into its category block. Every row states what the error is, so the mapping is
> mechanical. Component, acceptance and copy ids are unaffected.

## Purpose

Give someone the Google Docs surface they already know, on a file that is still markdown, and say
plainly which controls change the file and which only change the view.

**There is no right rail in Doc mode.** The body uses the no-right layout, because the margin is
carrying comments and a second rail would leave the page too narrow to look like a page.

### The four faces

The instruction was few fonts, and few is a number. The generator's own title attribute names them.

Face | What it is | What it does to the file
Google Sans | the product face | a span attribute, dropped by a plain reader
A serif | a reading face for long prose | the same
A mono | for anything that has to line up | the same
The system face | whatever the reader's machine has | the same

- **A face is never written as a new syntax.** The plan classifies font family and font size as
  needing an extension, carried by a raw span, and records that Google itself drops them on export.
- **So the face renders here, survives a PDF export, and is plain text everywhere else.** That is the
  honest scope, and the toast says it.
- **Four is the cap.** A fifth face needs a founders' decision, because the argument for few fonts is
  the same argument that stops this becoming a font picker.

### Which controls change the file

This table is the specification. It is the difference between a markdown editor with a page skin and
a second file format.

Control | Carrier | Reader with no editor sees
Style, headings | ATX headings | the heading
Bold, italic | CommonMark | the mark
Strikethrough | GitHub-flavoured markdown | the mark
Lists, checklist | CommonMark and task list items | the list
Table | a markdown table | the table
Image, link | CommonMark | the image, the link
Underline | a span carrier | the words, unmarked
Font face, size | a span attribute | the words, unmarked
Colour, highlight | a coloured span, and `==text==` for highlight | the words, unmarked
Alignment | a span attribute | the words, unaligned
Page break | an export marker | nothing
Page setup, margins, orientation | front matter keys, honoured on export | front matter
Comment, suggestion | the change queue and the version record, never the bytes | nothing

**The refusal rule, from the plan's section 7.** Doc mode carries a feature only if a stranger's
plain markdown parser still shows the author's meaning from the bytes on disk. Everything in the
lower half of that table passes because the words survive; only the decoration is lost.

### The properties panel, and why it is here

`docs/mvp0/SCREEN-CHANGES-2026-09-18.md:53` carries a research note rather than an instruction. Four of the top
fourteen all-time requests on the largest markdown forum are about front matter, and the named defect
is a properties editor that cannot hold nested keys.

- **`C059` must edit nested YAML**, not a flat list of string keys.
- It is the panel page setup lives in, which is what the toast means by page setup living in the
  front matter.
- It is `specified, not built`. No properties panel exists in the generator or in `src/`.

## Data contract

What | Direction | Port or store | Shape | When
Open file bytes | in | `DocumentReader.open(path)` | `{bytes, version, headHash}` | on entering the mode
Front matter | in | parsed from the same bytes | a YAML tree, nested | on every parse
Page projection | in | derived in the client | blocks with byte offsets | on every parse
Comment threads | in | `CommentReader.forDocument(id)` | threads anchored by content hash | on mount
Presence | in | `PresenceChannel.observe(docId)` | the people here now | continuous while live editing is on
A formatting change | out | `DocumentWriter.splice()` | a byte range and its replacement | on the control
A front matter change | out | `DocumentWriter.splice()` into the front matter block | the same | on commit in `C059`
A comment | out | `CommentWriter.add()` | text plus its anchor | on post
A suggestion | out | `ChangeQueue.propose()` | a proposal, never a write | in Suggesting mode
PDF export | out | `ExportService.toPdf(path)` | a rendered file | on request

- **A comment is not a file edit.** It is keyed to the document and a content hash, so it survives an
  edit that does not touch its anchor and detaches when it does.
- **Suggesting mode proposes; it never writes.** The proposal lands in the change queue and is
  accepted or rejected on S20.
- The projection is stateless. Closing Doc mode and reopening it rebuilds the page from the bytes.

## Keyboard and focus

- On arrival focus is in the page, at the position held in the other mode. The two modes share a
  cursor position, because they are two views of one file.
- The Google Docs marks work: Command B, I, U, and Command Shift X for strikethrough.
- Command Option 1 to 6 set heading levels, as they do in Google Docs.
- Command Option M adds a comment.
- The ruler takes no tab stop. It is a readout.
- The margin cards are one composite stop after the page, reachable without leaving the keyboard.
- Command Shift Y switches between markdown and Doc, which is the same key that switches back.

## Responsive

- The paper keeps its shape and its padding shrinks. It stays a page, because a page that stops
  looking like a page has no reason to exist.
- **The margin has no room at phone width**, so comment cards move into the right drawer and the
  anchor highlight stays in the text.
- The toolbar scrolls sideways rather than collapsing, so the face selector and the size stepper stay
  reachable. They are the controls this screen was changed to add.
- The ruler is absent under tablet width.
- Suggesting mode works on the phone.

## Desktop differences

- Printing goes through the system print dialogue and uses the same renderer as the PDF export, so
  the two agree.
- A local font installed on the machine is still not offered. The four faces are the four faces.

## What this screen must never do

- **Never rewrite the whole file to apply a formatting control.** Every control is a splice.
- **Never invent a syntax that a plain markdown reader cannot survive.** The refusal rule in the
  plan's section 7 is the test.
- **Never claim a colour, a face or an alignment survives outside this view and a PDF.**
- **Never offer more than four faces without a founders' decision.**
- **Never write a comment or a suggestion into the file bytes.**
- **Never let the properties panel commit invalid YAML.** Refuse, and leave the old block.
- **Never flatten a nested front matter key to make the panel simpler.** That is the defect the
  research named.
- **Never show the scope toast more than once per account.**
- **Never present Doc mode as a different file.** The toast names the file, and the tab does too.
- **Never add a right rail here.**
