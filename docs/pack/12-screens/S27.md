## Purpose

The same workspace on the dark tokens, so someone writing at night is not handed a white page.

## Entry and exit

Dark mode is a theme, not a route. There is no URL for it and nothing to leave.

how | what happens
The theme button in the header, component `C018` | Flips the theme for every open surface at once
Settings, the Appearance section of S28 | The same preference, set from a list of three rather than a toggle
First load, no stored preference | The operating system decides, through `prefers-color-scheme`
A second device, same account | Reads the account preference, so the two agree without being told
Exit | None. Every route renders in whatever theme is current, including S18 and the portfolio

**What exists today.** `[O]` `src/modules/app-shell/presentation/ThemeToggle.tsx` renders one
button that flips the `<html>` class between `light` and `dark`. The pre-paint script is
`public/theme-init.js`, loaded from `src/app/layout.tsx:69`. Verified by reading all three at
`0af3c90`.

## Data contract

what | direction | port or store | shape | when
Theme preference | read | `AccountPreferencesReader.get("theme")` in `src/modules/app-shell/application/ports.ts` | `"system" | "light" | "dark"` | On sign-in, and on every device that opens the account
Theme preference | write | `AccountPreferencesWriter.set("theme", value)` | the same union | On every change, debounced once per second
Theme preference, local cache | read and write | `localStorage`, key `sgnk-theme` | the same union as a string | Read before first paint, written on every change
Resolved theme | read | `window.matchMedia("(prefers-color-scheme: dark)")` | boolean | Only when the preference is `system`
Document class | write | `document.documentElement.classList` | `light` or `dark` | Before first paint, then on every change

**The port does not exist yet.** `[O]` `src/modules/app-shell/` has a `presentation/` folder and no
`application/` folder at `0af3c90`. The preference is stored in `localStorage` only, so it does not
travel between devices. S28 promises that settings live on the account, which makes this a gap
rather than a choice. `INFERENCE:` the local key stays as the pre-paint cache even after the account
port lands, because an account read cannot happen before first paint without a flash.

## Actions

action | trigger | what happens | failure behaviour | event id
Flip the theme | Click `C018` | The class flips, the local key is written, the account write is queued | The class and the local key still change. The queued write retries. Nothing blocks on the network | `ui.theme.changed`
Choose match the system | S28 Appearance, first option | The stored preference is removed and the media query decides | `E106` if the preference cannot be cleared | `ui.theme.changed`
Resolve at load | Page load | The script reads the key, or falls back to the media query, and adds one class | `E105`, and the light class is added, which is what the script already does at `public/theme-init.js:11` | `ui.theme.resolved`
Follow the system live | The operating system switches theme while the tab is open | Only when the preference is `system`. The class is re-resolved with no reload | Silent. The theme stays as it was | `ui.theme.resolved`

## States

state | when | what is shown | what the person can do
first-run | No stored preference and no account preference | Whatever the operating system asks for | Flip it, which creates the preference
empty | n/a | A theme has no empty state. There is always a resolved value | n/a
loading | Between the script running and React mounting | The correct theme already, because the class is set pre-paint | Everything. This is the point of `C144`
partial | Account preference read, local cache disagrees | The account wins and the cache is corrected in place | Nothing to do
offline | No network | The local key serves. The account write is queued | Flip freely
unauthorised | Signed out, on S01 or a published page | The operating system decides. There is no account to read | Nothing. A reader is not asked to hold a preference
over-cap | n/a | A theme is not metered. It is never an entitlement | n/a
AI-unavailable | n/a | No model call is made by this screen | n/a
conflict | Two devices set different themes within the debounce window | Last write wins on the account. Neither device is interrupted | Set it again
error | `localStorage` throws, as it does in a private window | The light class, from the script's own catch | Flip it for the session only
degraded | The account write keeps failing | The theme works locally and does not follow to another device | Nothing, and nothing is said, because saying it would be noise

## Keyboard and focus

- The theme button is in the header's tab order, after Search and before the account avatar.
- It is a real `<button>` with an accessible name that states the result, not the current state.
  `ThemeToggle.tsx` already does this.
- **No global shortcut.** `15-INTERACTION-AND-KEYBOARD.md` did not exist when this was written, so
  no conflict could be checked. `UNVERIFIED:` whether any chord is free for it.
- Focus does not move when the theme flips. Nothing is re-mounted.

## Responsive

- **The phone gets the same treatment as the desktop.** `[Z]` the founders' review of 18 September
  says the phone view is bland and needs the desktop's theme treatment, and says explicitly that it
  likely applies to more phone views than S01. `docs/mvp0/SCREEN-CHANGES-2026-09-18.md:19` to `:21`.
- So the dark pass covers the 52 px phone bar, the bottom bar's five items, both drawers, the sheet,
  and the grab handle, not just the document body.
- The browser chrome colour is already handled by `C145`, which is what stops the notch area
  reverting to white on the phone.
- Nothing is removed at phone width. The toggle lives behind More on the bottom bar, and the full
  three-way choice is in Settings.

## Desktop differences

- The Tauri build reads the same account preference and the same local key, so the desktop and the
  web agree.
- **The window chrome is the operating system's, not ours.** A macOS window set to the system's
  light appearance around a dark document is the one visible difference, and it is the platform's to
  fix, not ours.
- `UNVERIFIED:` whether `src-tauri/` sets a window theme at `0af3c90`. Not checked in this session.

## What this screen must never do

- **Never render a light frame before a dark one.** The pre-paint script exists for this and must
  stay inline and synchronous in `<head>`. Moving it into the bundle reintroduces the flash.
- **Never make match-the-system unreachable.** `[O]` it is unreachable today: `src/modules/app-shell/presentation/ThemeToggle.tsx:25`
  only ever writes `"dark"` or `"light"` and never removes the key, so the first flip is one way. A
  person cannot get back to following their operating system without clearing site data. This is a
  defect, severity `LOW`, and `A659` is its red proof.
- **Never gate the theme behind a plan.** It is not an entitlement and has no row in S35.
- **Never let the theme change what is written to a file.** The projection law applies here as
  everywhere: the bytes on disk do not know which theme rendered them.
- **Never ship a dark surface that was only checked on the desktop.** The phone is half the set.
- **Never use an emoji or a second icon library for the toggle.** Google Material Symbols, inline
  SVG, per `65-CONVENTIONS.md` section 9.

## Open questions

id | question | why it is open
`D53` | Is the theme preference part of the account, or of the device? | S28 says settings live on the account so every device agrees. A person who wants dark on a laptop and light on a phone is then stuck. The plan does not address it
`D54` | Does a published page, S18, follow the reader's system theme or the author's choice? | Neither `docs/mvp0/PRODUCT-PLAN.md` section 10 nor the S18 bullets say. The reader has no account, so `INFERENCE:` it must be the reader's system

**What is not specified here.** The exact dark values are not restated in this file, because they
live in `src/app/globals.css:78` and duplicating them would create the second copy that
`65-CONVENTIONS.md` section 1 forbids. Contrast ratios were not measured in this session, so nothing
here claims WCAG conformance. What would falsify this file: a decision that the theme is per device,
which would delete the account port from the data contract and rewrite `A658`.
