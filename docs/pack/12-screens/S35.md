## Purpose

Every limit the product enforces, in one editable table, so a cap is changed from a screen rather
than from a deploy.

## Entry and exit

**The panel ships. It is not deferred.** `[Z]` on 18 September the founders answered the question
they had been asked, `docs/mvp0/SCREEN-CHANGES-2026-09-18.md:307` to `:309`: the configuration panel
ships, carrying our recommended values as defaults, and the values are revisited later. That
**reverses** the instruction earlier in the same review, `:213`, which said later, build the product
first. The later answer wins.

**Why the reversal matters, in one number.** Plan revision 6 moved **eleven of the eighteen founder
questions** into this panel, section 29. Deferring the panel would have put all eleven back on the
table as hardcoded values needing answers before phase A. Section 30 makes it a phase A build for
the same reason in reverse: retrofitting it later means finding every hard-coded cap already written
into the product.

## Data contract

what | direction | port or store | shape | when
Plan rows | read | `PlanConfigReader.all()` | a value per entitlement id per plan | On opening the panel
Row history | read | `ConfigAuditReader.lastChange(entitlementId)` | who, from, to, when | On opening, one per row
Impact preview | read | `LimitsImpactReader.preview(changes)` | a count and the named accounts a change would move over a cap | Before a save, never after
Change set | write | `PlanConfigWriter.save(changes)` | the changed rows only, with the values they were read at | On confirming the save
Audit row | write | `ConfigAuditWriter.record(change)` | who, which setting, from, to, when, and how many accounts moved | Inside the same transaction as the save
Resolved limits, everywhere else | read | `limitsFor(account)` | the resolved set | On every cap check in the product

**Everything downstream reads one function.** Section 30: a single function, `limitsFor(account)`,
resolves a plan row plus any exception into the limit set, and nothing else in the product reads a
cap. A number appearing anywhere else is a defect, and the architecture gate is where it should be
caught, the same way `npm run arch` already catches a `process.env` read outside config and
infrastructure.

**That gate can be written today.** `specs/harness/clean-architecture-report.mjs`,
`specs/harness/import-boundary-report.mjs` and `specs/harness/server-folder-blocklist.mjs` all exist
at `0af3c90`, verified with `ls specs/harness/`. A cap-literal report is the same shape as the three
already there.

**`src/modules/config/` does not exist** at `0af3c90`, verified with `ls src/modules/`. Specified,
not built.

## Actions

action | trigger | what happens | failure behaviour | event id
Edit a cell | Typing in a value | The cell is marked as edited. The pending bar appears and counts it | `E048` when the value is not valid for that row's kind. The cell is marked and the save is blocked | `config.setting.changed`
See who | The pending bar control | The named accounts a save would move over their cap | `E653` when the impact cannot be computed. **The save is blocked**, because an unknown blast radius is not a small one | `config.impact.previewed`
Review and save | The pending bar control | The impact is shown and confirmed, then the rows are written and audited in one transaction | `E119` when a row changed underneath since it was read. Nothing is written and the conflicting row is named | `config.change.saved`
Discard | The pending bar control | Every edit is dropped. Nothing is written | None | `config.change.discarded`
Raise a limit | A save that only increases | Takes effect on the next read. Nobody notices and nobody is moved | The same as any save | `config.change.saved`
Lower a limit | A save that decreases below what some account holds | Those accounts enter the over-cap state of S33: everything readable and exportable, nothing new created | The same as any save, but the impact step is not skippable | `config.change.saved`

**A limit that falls is a downgrade, and section 30 says so.** Raising takes effect on the next read.
Lowering puts accounts into S33. So the panel states how many accounts a change puts over the line,
and names them, before it saves.

## States

state | when | what is shown | what the person can do
first-run | The panel opened before any change | Every row at its shipped default, with no last-change column filled | Edit
empty | n/a | A limits table with no rows would mean the product has no caps. Not reachable | n/a
loading | Rows being read | The table shell with the row names, values held | Wait. No cell is editable until its stored value is known
partial | Rows read, history not | Every value, with the last-change column showing that it could not be read rather than showing nothing | Edit and save. History is informational
offline | No network | Read-only, stated. **No editing at all**, because an edit that cannot compute its impact cannot be saved | Read
unauthorised | The account has no super admin flag | Not reachable. The route refuses on the server | Nothing
over-cap | n/a | A founder's own account can be over a cap, which changes nothing here | n/a
AI-unavailable | The chain is down | No effect. This screen makes no model call | Everything
conflict | Another founder saved a row while this one was editing it | The save is refused, the row is named, and both values are shown | Re-read and decide
degraded | The values read, but the impact preview is served from an account count taken minutes ago | Every row, and a pending bar carrying the time the count was taken | Refresh the impact, or save knowing the count may have moved
error | The rows cannot be read at all | One line and a retry. **No defaults are displayed**, because a guessed table invites a save of guesses | Retry
pending | Edits made, not saved | The table with edited cells marked, and the pending bar with the count and the impact | Save, discard, or keep editing
impact-unknown | The impact could not be computed | The pending bar shows the count and says the impact is unknown. **Save is disabled** | Retry, or discard

## Keyboard and focus

- Focus lands on the first editable cell, because a founder who opened this screen came to change
  something.
- Tab moves across a row then down, the way a spreadsheet does, so a run of related limits can be
  set without reaching for the mouse.
- Escape in a cell reverts that cell and leaves the others pending.
- The pending bar is reachable by Tab from the last cell and never traps focus.
- **No shortcut saves.** A save here moves other people's accounts, and a chord is the wrong way to
  start it.

## Responsive

- **The phone is read-only**, and the generator says so on the panel itself. Six rows are shown,
  each with its Free and Pro values.
- The pending bar does not appear on the phone, because nothing can be pending there.
- That is a deliberate narrowing rather than an omission: a save that moves named accounts over a cap
  is not a thing to do on a phone.

None. The Tauri build renders the same route, with the same server-side super admin check.

## What this screen must never do

- **Never let a second copy of a limit exist.** The invariant on the heading is the product's claim,
  and `A140` is how it stays true.
- **Never save without showing the impact.** Section 30 requires the count and the names before the
  write, not after it.
- **Never delete or hide an account's content when a limit falls.** Lowering moves accounts to S33,
  where everything stays readable and exportable.
- **Never check super admin in the browser.** Section 30 says server-side on every write.
- **Never write a change without its audit row.** One transaction, both rows, or neither.
- **Never allow editing from the phone.** A change here reaches other people's accounts.
- **Never move one account from this screen.** That is an exception and it belongs to S38, which is
  the difference between changing a plan and helping one person.
- **Never display a default when the stored value could not be read.** A guessed table invites a save
  of guesses, which is the one way this screen could do real damage.
