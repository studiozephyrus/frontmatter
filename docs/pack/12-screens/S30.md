## Purpose

One markdown file that is also my public page, with no build step and no second format to learn.

## Entry and exit

How a person arrives | Route or control
The tree, opening `portfolio.md` | The ordinary editor route for that file. There is no special editor
Settings, Sharing | A link to the file, and the handle claim if no handle is held
The published page itself | `frontmatter.in/@handle`, which any reader opens without an account
A template | Sharing offers a few starting files. `[Z]` the founders asked for a few templates

How they leave | What happens
Closing the tab | Back to the last document. The page stays live
Unpublish | The handle is released after a stated interval and the URL goes dark
Export | The file leaves as markdown, and the writing folder with it

**Two surfaces, one file.** The editor surface is the ordinary workspace showing `portfolio.md` in
Split. The public surface is the rendered page. The generator draws the desktop as the first and the
phone as the second, which is honest about where each is actually read.

**The seven front matter keys, which are the whole profile.**

key | holds | if absent
`name` | The display name | The handle is used
`handle` | The path segment after the at sign | The page cannot publish. `E300`
`title` | One line under the name | The line is omitted, not left blank
`links` | A map of named links | The chip row is omitted
`projects` | A list of entries, each with a title and a line | The Projects section is omitted
`writing` | A folder path | The Writing section is omitted
`theme` | A named theme | The plain theme is used

The list is `docs/mvp0/PRODUCT-PLAN.md` section 5. Section 10 gives the same seven and says that
all of them are ignorable by any other tool, so the file stays portable. The format carries
`portfolio: 1` as its version field, unknown keys are ignored and kept, and it degrades to ordinary
front matter in a plain reader. `docs/mvp0/PRODUCT-PLAN.md` section 20.

**No section is a container for a container.** The H2 headings in the body are the page's own
sections, rendered in document order below the generated ones.

## Data contract

what | direction | port or store | shape | when
The file | read | `VaultReader.getFile("portfolio.md")` | content and a blob sha | On opening the editor, and on each publish
The file | write | the ordinary splice writer | a byte range | On every edit, like any document
Parsed profile | read | `PortfolioReader.parse(content)` | the seven keys, plus the body | On render, in the editor and on the public route
Writing index | read | `VaultReader.listFolder(writing)` | path, title, date per file | On render
Handle | read and write | `HandleRegistry.claim(handle)` | one handle per account, case-folded | On claiming, and on every publish
Published object | write | `PublishWriter.put(handle)` | a rendered object plus the stored file | On publish
Entitlement | read | `LimitsReader.forAccount()` | `limits.portfolio`, `limits.branding.removal` | On opening, to decide the footer and the publish control

**Served from the stored file, with no build step.** `docs/mvp0/PRODUCT-PLAN.md` section 5. That is the
whole product claim on this screen: every generator opened for the research wanted a folder, a
config and a build, and this does not.

**`src/modules/portfolio/` does not exist** at `0af3c90`, verified with `ls src/modules/`. The
closest shipped thing is `src/modules/share/application/resolve-public-note.ts`, which resolves a
public slug for a single note. Specified, not built.

## Actions

action | trigger | what happens | failure behaviour | event id
Claim a handle | Type one, then confirm | The handle is checked, reserved, and written to the file's front matter | `E301` when it is taken, `E302` when the shape is not allowed. Nothing is written | `portfolio.handle.claimed`
Publish | Click publish | The stored file becomes reachable at the handle | `E300` when there is no handle, `E303` when the plan does not include the portfolio | `portfolio.published`
Edit | Type in the source pane | The splice writer replaces exactly the bytes that changed | The engine refuses rather than guess when a range is ambiguous, which is the ordinary editor behaviour | `doc.saved`
Apply a template | Pick one in Sharing | The chosen starting file is written as `portfolio.md` if none exists | `E304` when a file already exists. It offers to open the existing one and never overwrites | `portfolio.template.applied`
Unpublish | Click unpublish | The URL goes dark and the handle is held for a stated interval | `E305` when the object cannot be removed. The page stays and the state says so | `portfolio.unpublished`
Add a post | Create a file in the writing folder | It appears in the Writing section on the next render | A file that cannot be parsed is listed with its filename and no date, never dropped silently | `portfolio.post.added`

## What this screen must never do

- **Never require a build.** The page is the stored file rendered. A build step would make the file
  a source rather than the thing itself, which is the whole difference from every generator the
  research opened.
- **Never invent a second format.** Seven front matter keys, ignorable by any other tool.
  `docs/mvp0/PRODUCT-PLAN.md` section 10.
- **Never overwrite a person's file with a template.** `A305` is the red proof.
- **Never put a Follow button on it.** `docs/mvp0/PRODUCT-PLAN.md` section 5 says plainly there is no
  social feature in this plan, and one button would make it one.
- **Never load a third-party script on a published page.** It is the first of the eight security
  controls, `docs/mvp0/PRODUCT-PLAN.md` section 14.
- **Never gate the page behind an account.** The reader has no account and is not asked for one.
  This is the same rule that S18 was decided on, in `docs/mvp0/SCREEN-CHANGES-2026-09-18.md:325`.
- **Never write to the file to record a publish.** Publishing is a state about the file, not an edit
  of it, apart from the handle the person set themselves.
