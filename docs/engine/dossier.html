01 The starting point & the problem

This started as a question about a format — could there be a next-generation markdown? It ended somewhere more useful: the format is fine. What is missing is a compiler.

The original brief was mdz — a next-gen markdown. Three weeks of measurement moved the conclusion twice, and the final position is narrower and much more defensible than the starting one.

The problem, stated precisely

A markdown file is a string. Every tool that edits it — an editor, an agent, a formatter, a colleague's git push — hands you back a different string with no record of what changed. So nothing in the file can be referred to twice. A comment thread, a backlink, an outline entry, a cross-file link to a heading: each is a pointer into text that will move, and nothing can tell you where it went.

Every other document system solved this. None solved it under our constraint.

SystemAnchorSurvives an out-of-band edit?Why it works for them
Wordzero-width sentinel pairsyesthe artifact is XML; an invisible marker is free
Notiona UUID on the blockyesthe artifact is a database
Overleafinteger offsets in an OT sidecarnothey own every write to the file
ProseMirror / CM6offsets remapped through a change mapnothe remap needs the op that caused the change

Overleaf is the only published system with our exact constraint — the artifact must stay a plain text file another tool can read — and it survives only by owning every mutation. We cannot. A git pull yields a new string with no op stream. A vim edit yields no op at all.

So the thing to invent was never a syntax. It was an anchor that survives the git boundary.

03 How markdown actually works

Understanding the pipeline is what makes the design decisions obvious rather than arbitrary.

source.md text
→
block passparagraphs, lists, fences
→
inline passemphasis, links, code
→
ASTmdast — the tree
→
transformhast — HTML tree
→
renderHTML string

How to read it

Markdown is parsed in two passes, not one — block structure first, then inline markup inside each block. That two-pass design is why **bold** cannot span a paragraph break, and why a fence's contents are invisible to every inline rule.

The arrow into the AST is one-way. Everything after it is a projection. This is the single most important fact in the whole document.

The AST is lossy, provably. Foster et al. (TOPLAS 2007, Lemma 3.9) prove a total well-behaved lens whose put ignores the original source requires get to be a bijection. "Regenerate from the AST" is definitionally such a lens. We measured what that costs:

MeasurementResult
CommonMark spec examples that are two distinct sources with an identical AST443 of 655
Lines rewritten by a zero-edit round trip of a real 206 KB document24.98%
Bytes dropped by the same round trip18.94%
Files in this repo surviving parse → stringify byte-identically0 of 51

mdast-util-to-markdown's own documentation says it plainly: "complete roundtripping is impossible." This is not a bug to tune away — it is mathematically excluded. Hence the first invariant: splice, never regenerate.

And what the tree can hold is closed. A .md file carries exactly one data structure: a finite, ordered, rooted tree over a closed 21-label alphabet with string leaves. It cannot carry types, identity, null, or any edge that is not parent–child. That is the tree/graph boundary — not a syntax gap a dialect could close.

Three lessons, and they point the same way.

New dialects do not win. djot has CommonMark's own author and is invisible. The reason is not quality — it is that markdown's value is its universality, and a dialect forfeits exactly that.

Fence dispatch wins because it costs nothing. CommonMark, verbatim: "Although this spec doesn't mandate any particular treatment of the info string, the first word is typically used to specify the language." That refusal to define semantics is the extension point. A renderer matches one string and replaces the node; every non-participating tool degrades to a code block.

And the sobering one. Faced with its own largest format gap — Dataview, 4.65M downloads — Obsidian did not extend markdown. It shipped .base (YAML) and .canvas (JSON, whose edges are directed, labelled, typed). The two things markdown provably cannot express each got a non-markdown sidecar. The best-resourced actor in this ecosystem concluded markdown was the wrong place. We answer that in §08.

~41 ms for a 446 KB / 2,225-block document. All 14 false matches were hand-audited, not sampled: 4 are oracle artifacts, 6 a bulk migration, 3 list drift, 1 a table rewrite. Genuine substantive errors: 10 in 28,170 = 0.036%.

Three results overturned our own earlier design. Rigid context fingerprints get worse as the window grows. Content-defined chunking is the wrong granularity. And every position-based tiebreak made things dramatically worse — content-hash plus nearest-position goes from 0.00% to 22.20% false. Refusing is cheap. A silently wrong anchor is not.

What the demand data says

6,047 Obsidian plugins, 132,834,339 cumulative downloads. Classifying the top 300 — 83.9% of all demand — by what kind of gap each plugin fills:

Two-fifths of revealed demand is markdown failing to express something — and the app column is smaller, which is the opposite of "markdown is fine, the apps are limited." It replicates on three populations sharing no mechanism: plugins 40.1%, forum requests 39.0%, VS Code extensions 35.4%.

The causal proof is Logseq. Its format natively has block IDs, properties, a query language and spaced repetition. Obsidian has 70 spaced-repetition plugins; Logseq has 2, and both are merely Anki bridges. Query: 46 vs 20. Tasks: 149 vs 30. Kanban — which neither format helps — 63 vs 6. Logseq is a worse app, yet every cluster matching a native format feature is 10–35× smaller.

When the format absorbs a capability, the plugin ecosystem for it collapses.

The wedge, from the incumbent's own source

Obsidian's processFrontMatter destructively rewrites frontmatter — strips quoting, deletes YAML comments outright, destroys explicit type tags. Their own type declaration:

export interface FrontMatterCache { [key: string]: any; }

Every property in every note, in the market-leading markdown app, is any. Demand ratio: Dataview 4.6M downloads against the best frontmatter validator at 2,000 — 2,300×. And Obsidian has publicly declined to fix it: "The decision we made is for plugins to be able to interact with frontmatter easily."

What breaks outside English and outside Latin

Four results that constrain the design more than they look:

  • NFC decomposes Bengali ড়/য়/ঢ় (composition exclusions), so "just normalize everything" rewrites 77 of 437 lines of a real poem in your vault. ⇒ normalize the comparison key, never the bytes.
  • Emphasis fails outside Latin when punctuation sits inside the delimiter — **注意：**该文档 is literal asterisks in all four engines. Open as commonmark-spec#650 since 2020.
  • Markdown's link syntax is built entirely from bidi-mirroring characters — [ ] ( ) < > { } all mirror; * _ - # do not. RTL source visual order cannot match logical order. A structural limit of the format.
  • Automated accessibility checkers are blind to markdown. axe-core fires 7 of its 105 rules; 98.5% of 11,695 violations trace to two causes in page chrome. Every content-level defect scores zero — because ![](x) compiles to alt="", which is valid: it asserts "decorative."

That last one is not a complaint. It is the clearest capability gap we found, and §08 turns it into a product.

06 Taking markdown to the next level

The answer to "why can't we have folder trees, self-including files, new representations?" is we can — through dispatch, never through new syntax. There are exactly four channels.

TierChannelA dumb viewer seesProven by
1frontmatternothinguniversal; TOML is 0 of 42,643 files — YAML is the only vocabulary
2fence info stringa normal code block30 uncoordinated platforms render mermaid
3HTML commentnothingnodejs/node ships 4,310 <!-- YAML instances
4derived, never stored—graphs, outlines, site maps

What we must never do is spend a sigil. Markdown has ~32 punctuation extension points. From jgm: "Guaranteeing that any extension is compatible with any other one is not feasible, as two extensions may want to interpret the same character for two different purposes." That is character-namespace exhaustion — resource exhaustion, not governance. And it is live today: Spaced Repetition's card separator is ::; Dataview's inline field is key:: value. Two top-50 plugins, same two characters, colliding right now.

The last two matter most because they are supply-starved: enormous demand, near-zero supply. That is the signature of a gap a plugin cannot close. A board can be faked by overloading headings; a typed link needs the link itself to carry the relation, and no plugin can retrofit that. Obsidian conceded exactly this — .canvas has edges because markdown could not.

Enhancement on top of markdown, the way MDX did it

MDX's actual lesson is a warning, and it is not about adoption. MDX cannot write the document back out. Markdoc's format() is byte-identical and idempotent; MDX has no equivalent and cannot, because arbitrary JavaScript does not losslessly re-serialize. For a product that edits and saves, that is disqualifying — independent of market share entirely. MDX also silently miscompiles valid CommonMark: the set {1,2} renders as the set 2, with no warning at any stage.

Take MDX's ambition. Refuse MDX's mechanism. Extension goes through dispatch, and the file stays readable by everything.

07 Your notation idea, answered

You sketched something like ``X`` … ``X`` — a paired marker that means "this is an image", or a table, or whatever we declare, with only frontmatter knowing what it means. The instinct is right. One detail decides whether it works.

What fails

Inventing a new delimiter in prose. Any new sigil spends a non-renewable resource, collides with the ~8 incompatible ecosystem dialects already in the wild, and — critically — fails silently. The model writes ~ doing instead of ~doing, the renderer does not match, and the field vanishes. The document still looks like a document. Nothing throws.

What works

Declaring a vocabulary inside a construct that is already opaque. A fenced block and a code span are inert everywhere — every markdown tool on earth already renders them as literal text and refuses to interpret their contents. Put the notation there and degradation is guaranteed by the spec, not by luck.

So your ``X`` idea, in its safe form, is a declared vocabulary carried by an existing opaque construct:

---
fm:vocab:
  due:
    carrier: inline-code
    examples: ["`due:2026-08-01`", "`due:friday`"]     # 2-3 worked instances
  figure:
    carrier: fence
    examples: ["```fm:figure\nsrc: a.png\ncap: Fig 1\n```"]
---

Ship the migration `due:2026-08-01` before review.

```fm:figure
src: diagram.png
cap: The seven passes
```

Open that file anywhere else and you see inline code and a code block. Nothing breaks, nothing is lost, no tool errors. Open it in frontmatter and the compiler binds due to a date type, checks it, indexes it, and projects it into the graph.

The three rules that govern this — all measured

RuleEvidence
1. Declare by EXAMPLE, never by rule.Aycock et al. ablated MTOB: "almost all improvements stem from the book's parallel examples rather than its grammatical explanations" — and flatly, "no evidence that long-context LLMs can make effective use of grammatical explanations." Replicated across three languages.
2. Cap the vocabulary in single digits.IFScale, 20 models, 7 providers: "even the best frontier models only achieve 68% accuracy at the max density of 500 instructions." Plus primacy bias — and the geometry is hostile: the declaration sits at the top of the file where compliance is highest; the constructs must fire in the fortieth note, where it is lowest.
3. The renderer is the write gate. No constrained decoding.Coverage on complex schemas: Guidance 41%, llama.cpp 39%, XGrammar 28%, Outlines 3%. Naive masking "distorts the output distribution" — valid strings that are bad. Validate-and-repair gets the same guarantee at no distribution cost.

Plus one hard rule: never redefine a symbol CommonMark already defines. Declaring a new denotation is safe (140/140 in our test). Redefining a procedure is not (98.2% → 38.6%).

The measurement that decides the operating point has not been made

Every number above is Opus-class, five constructs, declaration in immediate context. The model that will actually write into a user's file in an editor is smaller and faster, and every published curve says that is precisely where format adherence collapses. The experiment establishes a ceiling, not an operating point. This must be re-run against the production model before any notation feature ships.

08 Frontmatter as the first renderer

The honest answer is better than lock-in: exclusivity comes from capability, not captivity. The files stay portable on purpose — that is what makes them safe to adopt, and safety is the acquisition mechanism.

The same bytes, in any other tool

Renders as ordinary markdown. The notation is inert text. Nothing breaks, nothing is lost.

The same bytes, in frontmatter

The compiler reads the declaration, binds and type-checks the constructs, keeps block identity across every edit, and projects graph, outline and site.

Why the capability gap is durable

  1. Identity is the moat, not expressiveness. A sidecar file can add expressiveness — Obsidian proved it twice. A sidecar cannot give you identity across an out-of-band edit. That requires re-deriving the anchor from content, and no competitor has built it.
  2. The editor sees the save. Drift detection without a diff is near-unsolved — a trivial heuristic scores F1 68, beating every post-hoc neural model at 66–67. Handed the edit, neural reaches 77–81. Nobody else is handed the edit.
  3. The wedge is publicly refused. Competitors do not accidentally close a gap they have declared they do not want to close.
  4. The diagnostics require markdown-awareness by construction. We found remark-math swallowing prose between two $ signs — 36 captures in 20 of 272 files — producing zero axe violations. A parser mis-tokenization creating a real defect that only a markdown-aware compiler can see.

The acquisition strategy — the mermaid playbook

You cannot force adoption of a portable format, and trying is what kills formats. What you can own is being the reference implementation of something everyone wants. Mermaid is the proof: the syntax was free, nobody was forced, GitHub adopted it, and 30 platforms followed. The spec was the giveaway; the tooling was the product.

1 · publisha page rendered by the engine, rich and correct
↓
2 · curiosity"the source is plain markdown — how is it doing that?"
↓
3 · zero-risk trialthe declaration is in the file; their existing vault still opens everywhere
↓
4 · the CLIfrontmatter check in their CI — value with no editor at all
↓
5 · the editorthe only place identity, drift and the YAML wedge exist

How to read it

Steps 1–3 are free and open — the format degrades, so trying costs nothing and leaving costs nothing. That is what makes people willing to start. Steps 4–5 are where the compiler is required, because identity-across-edits and save-time drift cannot be reimplemented by someone reading the file.

Publishing benchmark B1 (§11) is the accelerant: it makes the problem legible to the whole industry, with us holding the only good answer.

09 Fusing into the AI OS

This is the part with the least friction, because the AI OS is already markdown-native — and currently runs on unchecked markdown.

The sharpest fit is a bug class you have already been bitten by. Learned Rule #59 records three instances of a producer writing one field name and a consumer reading another — tokens_in vs input_tokens, pass vs assertion_pass — each silently publishing a wrong number for weeks, because a missing key coerces to a falsy default indistinguishable from a real negative. That is exactly what a typed interface pass catches at author time.

Sequencing matters, and Learned Rule #43 already prescribes it: build in hierarchy order. The engine enters at the data layer (trace rows, validated skill frontmatter), never at the routing layer. And per Rule #38 nothing goes dev→live: offline eval → shadow → promote.

10 The plan

Seven passes. Each phase carries a gate that can stop it — a phase without a falsifiable gate is a wish.

1  parse       .md → AST + byte positions       incremental
2  identify    mint / recover block anchors     ← the invention
3  interface   frontmatter → module signature   schema INFERRED, never demanded
4  resolve     bind every cross-reference       unresolved = diagnostic, never a silent drop
5  index       symbol table + reverse index     → outline, tags, backlinks
6  check       schema · links · drift           → the confidence ladder
7  project     outline · graph · site · tokens  never stored
PhaseShipsKill-gate
1 · core/splice writer, anchors, the YAML wedge100% byte-fidelity on untouched regions across 50 files, verified by an independent oracle — the current check uses the writer's own code path and cannot catch an offset bug
2 · resolve/ + check/linker, symbol table, frontmatter check CLIper-class precision across md's 4,117 files
3 · schema/infer → propose → acceptfalse-positive rate on a corpus verified to be human-authored. Above ~0.4 and users disable it permanently
4 · pack/unpackcontainer + edit-mapping back to source filesbyte-identical unpack proven by per-file digests
5 · reconcilerprose ↔ code drifttier I only at first

Two rules keep it usable. A diagnostic may only reach tier E (fails the build) if a human accepted the constraint that produced it — inferred schemas start at Warn; accepting the proposal is what converts advice into a guarantee. And a scope check from our own data: a compiler over 833 files found 365 true problems touching only 112 files (13.4%), so a random note has an 86.6% chance of an empty panel. A vault-level check command is earned by this data; a persistent Problems panel is not.

The rule that governs every benchmark here

A benchmark whose subject is a rare fault proves nothing until it reproduces the fault. A green suite is the expected result of running it, not evidence of correctness. Every gate must be demonstrated to fail against the unfixed implementation before its pass is reported. We have been burned by this twice already.

The risk, recorded rather than buried

Obsidian, holding every advantage, looked at these same gaps and shipped sidecar files twice. The best-resourced actor in this ecosystem concluded markdown was the wrong place to put them.

Our differentiator is identity across edits — which a sidecar cannot provide. Not expressiveness, which a sidecar provides perfectly well. If we ever find ourselves competing on expressiveness, we have lost, because .canvas already won that fight.
