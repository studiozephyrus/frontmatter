## Purpose

See every change waiting on this document, know who or what made each one, and accept or reject them
one at a time.

## The two rules this screen exists to carry

**First: human work and machine work are never combined into one undifferentiated list.** A filter
sits across the top with three positions, All, People, and AI and agents. The founders made it a
general rule on 18 September, not a per-screen instruction, at
`docs/mvp0/SCREEN-CHANGES-2026-09-18.md:296`. The stated reason is cognitive load, and it applies to
every screen that mixes the two.

**Second: accepting in bulk is a human-only affordance.** Accept all applies only to one named
person's edits, and it confirms the count before it runs. **AI and agent items are accepted one at a
time, with the diff shown.** That is the plan at `docs/mvp0/PRODUCT-PLAN.md` section 5, at line 545,
and it is backed by four studies on over-acceptance of machine-written text, at
`docs/mvp0/PRODUCT-PLAN.md` section 5, at line 551.

**Accept, Reject and Reply carry equal weight.** Same size, same prominence, same order on every row.
No default, no primary, and nothing pre-selected.

highlighted, because a change with no surrounding text is not reviewable.

**Three item shapes, not one with a badge.** A person's change, an AI edit and an agent's write are
drawn differently because they carry different risks and different controls.

Source | Leading control | Bulk accept | Diff
A named person | Accept | Yes, after confirming the count | On request
An AI edit you asked for | Accept | Never | Always shown inline
An agent that wrote the file on disk | Show diff first | Never | Required before accepting

## Data contract

What | Direction | Port or store | Shape | When
Queue | read | `ChangeQueue.forDocument(documentId)` | `{ id, source, author, ask, span, proposedBytes, at }` | On open, and on every arrival
Counts per source | derived | the same read | `{ all, people, machine }` | With the queue
Document bytes | read | `ProjectFiles.read(path)` | The bytes on disk | With the queue, to place the spans
Accept | write | `ProjectFiles.splice(path, span, proposedBytes)` | One splice, one new version | On each accept
Reject | write | `ChangeQueue.reject(id)` | The item is closed. The file is untouched | On each reject
Reply | write | `Comments.add(documentId, span, body)` | A comment against the span, not a change | On each reply
Version mark | write | `VersionRecord.append` | `{ author, source, model, ask, accepted_by, at }` | On each accept
Entitlement | read | `limitsFor(account)` | `limits.history.days`, for the history row | On open

**None of this is built.** At `0af3c90` a search of `src/` for a change queue, a proposal type or a
review store returns nothing. The whole screen is **specified, not built**.

**Attribution lives in the version record, not in a sidecar.** The per-span read state of the earlier
plan was dropped on 17 September and does not exist in the code. The fields above are the format the
plan specifies at `docs/mvp0/PRODUCT-PLAN.md` section 20, at line 1510.

**An accept is a splice.** The engine locates the span and replaces exactly those bytes. If the span
is ambiguous it refuses, and the item stays in the queue.

## Actions

Action | Trigger | What happens | Failure behaviour | Event id
Open the review | The rail row, or the toolbar pill | The queue loads, the rail switches, the spans light up | Queue unreachable, so `E360` and the rail keeps its usual rows | `doc.review.opened`
Filter | The three-position control | The list shows one source. The counts do not change | none | `doc.review.filtered`
Accept one | Accept on any row | The span is spliced, a version is written with its attribution, the item leaves the queue | Span ambiguous, so `E084` refuses, the item stays, and the file is untouched | `doc.change.accepted`
Reject one | Reject on any row | The item is closed. Nothing is written to the file | none | `doc.change.rejected`
Reply | Reply on any row | A comment is added against that span. The change stays waiting | Span no longer present, so `E361` and the comment attaches to the document | `doc.change.replied`
Show diff first | The agent row's leading control | The diff opens. Only then does an accept control appear | Proposed bytes missing, so `E362` and the item is closed as stale | `doc.change.diff.shown`
Accept all for a person | The bulk control | A confirmation states the person's name and the exact count, then splices them in order | Any one span ambiguous, so that one is left in the queue and `E084` names it | `doc.change.accepted.bulk`
Highlight a span | Focusing a row | The matching span scrolls into view and is emphasised | Span not placeable, so the row is marked stale and no highlight is drawn | `doc.change.focused`
Queue reaches zero | The last item cleared | The rail returns to its usual rows | none | `doc.review.emptied`

**`E084` is a refusal, and refusing is a correct outcome here.** Returning the file unchanged when a
range is ambiguous is the product's whole differentiation. Guessing is not an option, in bulk or
alone.

## States

State | When | What is shown | What the person can do
first-run | The first change ever queued on this account | One line saying nothing is applied until it is accepted | Read it, then review.
empty | Nothing waiting | The rail keeps its usual rows. The review row shows no count | Carry on writing.
loading | The queue is being read | The filter and the shapes render. Rows fill in | Wait.
partial | Some items placed, some spans not yet resolved | Placed items are reviewable. Unplaced ones are grouped and marked | Review the placed ones.
offline | No connection | The queue read from the last snapshot is readable. Accept and reject are disabled with one reason | Read, plan, come back.
unauthorised | The viewer's role may not apply changes | Items are readable. Accept is absent, Reply stays. The matrix at `docs/mvp0/PRODUCT-PLAN.md` section 19, at line 1473 governs it | Read, reply.
over-cap | n/a. Reviewing costs no credits and no quota | n/a | n/a.
AI-unavailable | The provider is down | Queued AI items stay reviewable. Only making new ones is blocked, on S32 | Review what is there.
conflict | An item cannot be placed because the file moved under it | The item is marked stale with its original text kept. Serious cases go to S31 | Open the diff, reject, or resolve on S31.
error | An accept threw after the splice was located | The file is left untouched and the item stays in the queue | Retry, or reject.
degraded | More items than the list can usefully show | Grouped by source and by author, with counts, newest first | Filter, or accept per person.

## Keyboard and focus

key | does
Tab, Shift Tab | Moves through the filter, then the rows, then the bulk control
J, K | Next and previous item, without leaving the list
A | Accept the focused item
R | Reject the focused item
C | Reply to the focused item
D | Show the diff for the focused item
1, 2, 3 | Move the filter to All, People, or AI and agents
Escape | Closes the rail and returns focus to the document

**Focus on arrival is the first item in the list**, not the bulk control. The bulk control is the
riskiest thing on the screen and should never be one keystroke from arrival.

**Accepting never moves focus onto another accept control.** After an accept the focus lands on the
next item's first control, which is not Accept for an agent row, so a held key cannot walk the queue.

**UNVERIFIED:** `15-INTERACTION-AND-KEYBOARD.md` lists no bare single-letter bindings, so `A`, `R`,
`C`, `D`, `J` and `K` are free. They are safe here only because this screen is not an editing
surface, and they must not leak into one.

## Responsive

- **The rail becomes the right drawer**, 300 px over a backdrop, reached from the toolbar count.
- **The filter stays across the top of the drawer**, because it is the one control that makes the
  list readable.
- **The three controls stack to full width** at thumb height on each row.
- **Tapping a row closes the drawer and scrolls to the span**, then reopens on the back gesture,
  because a phone cannot show the rail and the text at once.
- **The bulk control sits at the foot of the drawer**, behind a scroll, never within reach of a
  mis-tap.

## Desktop differences

- **The agent source is real on the desktop.** A watched folder means an agent can edit a file on
  disk, and that write enters this queue rather than the document. On the web the agent source only
  exists through a connection or a token.
- **The diff can be opened in an external tool**, because the desktop build has the file system.
- Everything else is identical.

## What this screen must never do

- **Never combine human work and machine work into one list.**
- **Never bulk-accept an AI edit or an agent write**, however many there are.
- **Never accept an agent write before its diff has been shown.**
- **Never guess an ambiguous span.** Refuse, keep the item, leave the file alone.
- **Never apply anything without a person pressing accept.** No silent merge, ever.
- **Never make Accept more prominent than Reject.**
- **Never run a bulk accept without stating the count first.**
- **Never lose the original text of a stale item.**
- **Never write review state into the document.** Attribution lives in the version record.
